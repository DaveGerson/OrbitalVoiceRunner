# Chunk 3 — Command Proposal, Permissions & Approvals — Quality & Correctness (SECURITY-CRITICAL)

**Score: 5.5/10** — The primary `propose_command` gate is genuinely airtight (single pure `decideProposal`, mandatory atomic claim, exactly-once dispatch, redaction), but a SECOND write path — `handoff_context_between_panes` — bypasses the Human-in-the-Loop gate entirely, and the auto-execute path can crash on a ledger-only pane. The core is excellent; the perimeter has a real hole.

## Findings

- **`server.ts:1823-1853` (`handoff_context_between_panes`) — CRITICAL — Writes model-controlled text to a target pane's stdin WITHOUT the Human-in-the-Loop gate.** This is a write path (`targetTerm.writeInput(commentCommand)` at 1849) but it only checks `Read-Only` (1836); for `Human-in-the-Loop` (or Full-Auto-equivalent) panes it dispatches with NO operator approval and NO pending entry. The injected block embeds `context_notes` (model-controlled) and is multi-line; for an `interactive_cli` agent pane each `\n` submits a line to the agent, so the model can push arbitrary instructions into a target agent pane bypassing HiTL. The code's own comment (1829-1832) flags the TODO. Real-world impact: the supervisor's "every agent command must be approved" guarantee (Journey 2) is breakable via this one tool. Fix: route the handoff write through `dispatchProposal` (same effective-mode + pending-approval gate).

- **`server.ts:1339-1343` (`dispatchProposal` auto_execute) — HIGH — `term!.writeInput` crashes on a ledger-only pane in Full Auto.** `paneExists` (1318) is true when the pane exists only in the ledger (`wsProj.panes[targetId]`) with no live terminal, but `auto_execute` non-null-asserts `term!` (1341). `propose_command` against a restored-but-not-spawned / dead pane id in Full-Auto mode throws `TypeError: Cannot read properties of undefined (reading 'writeInput')`. Because the entire `onmessage`/toolCall loop has NO try/catch (`server.ts:1380-1887`), the exception escapes into the Gemini SDK callback: `call.id` is never answered, the model hangs awaiting the tool result, and the session may destabilize. Fails closed (no command runs) but breaks the conversation. Fix: in `auto_execute`/`pending_approval`, require a LIVE terminal (`if (!term) return error_no_pane`) — `paneExists` should distinguish "live" from "ledger record" for write decisions.

- **`server.ts:1486-1887` (toolCall loop) — HIGH — No try/catch around any tool handler.** Any throw in any handler (the auto_execute crash above, a malformed `args`, a ledger op on a missing project) escapes the SDK `onmessage` callback, leaving `call.id` unanswered and the model stuck. Each tool branch should be wrapped so a failure returns an error tool-response and the conversation continues.

- **`server.ts:1202-1208` (`applyResolution` approved) + global-mode TOCTOU — MED — A pending HiTL command approved AFTER the effective mode changed to Read-Only still executes.** The mode gate is evaluated only at PROPOSAL time (`decideProposal`); `resolveDecision`/`applyResolution` re-check only pane existence, not the current effective mode. If global mode is flipped to `Read-Only` (or the pane demoted) while a command sits pending, an operator/voice approve still calls `writeInput`. For a safety-policy system this is a gap: the "Read-Only now" intent should void in-flight pending writes. Fix: re-evaluate `effectiveModeFor(record.terminalId)` inside the approve branch and block if Read-Only.

- **`server.ts:1674-1687` (`create_pane`) + Full Auto preset interaction — MED — A model can create a pane in `Full Auto` and immediately auto-execute on it within the same conversation.** `create_pane` accepts `permissions_mode: "Full Auto"` from the model with no operator gate, and the very next `propose_command` to that pane auto-executes. Combined with the missing input validation, the model can self-provision an unsupervised execution surface. Whether this is in-scope depends on threat model (the operator "started" Janus), but it means autonomy escalation does not require an operator action. Worth an explicit operator confirmation on Full-Auto pane creation.

- **`src/App.tsx:2252-2261` (ApprovalDialog stacking) — LOW — Concurrent pending approvals render as overlapping `fixed inset-0` modals.** With ≥2 pending, dialogs stack on top of each other; only the topmost is reachable, so the operator can't see/act on the others without resolving the front one. The server claim gate prevents double-dispatch, so this is UX-correctness not a bypass, but it degrades the multi-pane supervisor journey.

- **`server.ts:1267-1273` (WS auth) — LOW (acceptable) — Auth is a single shared per-process token auto-seeded to any page loader.** Correctly blocks cookie-less WS upgrades and CSRF (httpOnly + SameSite=strict), but it is not user authentication — anyone who can load the page gets the token. Documented in README's security note; flagging only for completeness. The `!==` comparison is non-constant-time but same-origin so timing attack is not practical.

## Does-it-do-the-job verdict
The headline `propose_command` → gate → approval → dispatch flow is correctly and defensively built and is genuinely airtight against double-dispatch and kind-bypass. But it is NOT the only write path: `handoff_context_between_panes` is a real HiTL bypass, and the auto-execute crash plus the un-try/caught tool loop make the gated path itself brittle. As shipped, the "every command is gated" guarantee is false.

## Top fixes
1. **CRITICAL** — Route `handoff_context_between_panes` writes through `dispatchProposal` (effective-mode + HiTL pending), not just a Read-Only check.
2. **HIGH** — Require a LIVE terminal for `auto_execute`/`pending_approval` (don't `term!` on a ledger-only pane) and wrap the entire toolCall loop in try/catch so a throw answers `call.id` with an error.
3. **MED** — Re-check `effectiveModeFor` at approve time so a pending command voids if the pane became Read-Only after proposal.
4. **MED** — Gate `create_pane` with `permissions_mode:"Full Auto"` behind an explicit operator confirmation (prevent silent autonomy escalation).
5. **LOW** — Render concurrent ApprovalDialogs as a non-overlapping queue/list.
