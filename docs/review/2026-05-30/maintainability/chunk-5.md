# Chunk 5 — Ledger, Projects/Knowledge, Orchestration Plans & Settings — Maintainability

**Score: 5/10** — `ledger.ts` and `types.ts` are clean (atomic-write persistence, single shared type source). But this chunk is where the two god-files hurt most: orchestration plan-advancement is a ~130-line nested closure in `server.ts`, settings logic is split across `terminal.ts` + a 1278-line `SettingsDialog.tsx`, recipes are hardcoded inline, and the ledger's persistence model is bypassed via `ledger["save"]` bracket-access.

## Findings

- **`ledger.ts` is solid.** The persistence layer does proper atomic writes (temp-file + rename, ledger.ts:69-107), debounced async save with a sync flush escape hatch and a dirty/saving reentrancy guard (ledger.ts:39-88). CRUD methods are small and single-purpose. `getProjectBriefing` (ledger.ts:181-193) cleanly shapes the `switch_context` payload. Good.
- **`types.ts` is the single source of truth for shared shapes** (PaneMeta/Workspace re-exported from ledger, types.ts:25-29; `frontend-safe, no fs` per the D7 comment). This is the right pattern and is well-executed.
- **BUT the four permission-mode strings and the preset strings are re-declared as inline string-literal unions ~15 times across `types.ts`** (lines 9,10,38,40,63,106,117,129,140,160,161) instead of named type aliases (`type PermissionsMode = ...`, `type ToolPreset = ...`). Every interface re-spells `"Full Auto" | "Human-in-the-Loop" | "Read-Only"`. One typo or one new mode = a 15-site edit with no compiler help.
- **`handlePlansTrigger` (server.ts:364-510+) is a ~150-line god-function** with 4-deep nesting and the attention-push triple (`push` + `pruneAttention()` + `broadcast`) copy-pasted at least 3 times inside it (server.ts:390-400, 415-425, 483-493). The plan state machine (advance / pause-on-missing-pane / pause-on-no-session / gate-next-step / complete) belongs in a pure, testable `advancePlan()` module mirroring how `decideStatus`/`decideProposal` were extracted; instead it is welded into the output-event handler with side-effects inline.
- **`ledger["save"]` bracket-string access appears across server.ts** (e.g. server.ts:1729,1751,1790,1877) to call a method that is actually `public save(sync)` — so the bracket form is not even bypassing visibility; it is a misleading idiom suggesting a private method. Worse, `save(true)` vs `save(false)` is an unlabeled boolean meaning sync-vs-debounced; call sites give no hint. A named `saveNow()` / `saveDebounced()` pair would remove both smells.
- **Orchestration recipes are hardcoded as an inline `const recipes = [...]` literal in `server.ts:877-897`** with fabricated demo commands (`echo 'Frontend running' && npm run dev`). They are config/data, not server wiring — they belong in a data file or a `recipes.ts`, and there is no `TemplateRecipe[]` type annotation on the literal (the `as const` casts are sprinkled per-field instead).
- **Settings logic is smeared across three layers with no validation seam:** `getDefaultSettings`/`loadSettings`/`updateSettings` in `terminal.ts:562-672` (deep manual per-key spread merges, easy to forget a new key — and indeed `secrets` and `announcements` need special-case merge handling), the sanitize/merge-on-PUT in `server.ts:1100-1123`, and a **1278-line `SettingsDialog.tsx`**. The API-key masking logic exists in two places (server.ts:1102-1108 masks on GET, server.ts:1113-1114 un-masks on PUT, terminal.ts:603 seeds `CONFIGURED_IN_ENV`) — a fragile three-point dance around one secret with magic sentinel strings (`"CONFIGURED_IN_ENV"`, `"••••"`).
- **`SettingsDialog.tsx` at 1278 LOC is the second-largest component** and almost certainly mixes presentation for every settings domain (voiceAi, presets, advanced, announcements, secrets) in one file — a prime candidate for per-section splitting. (Not read line-by-line per the slice guidance, but the size alone is a maintainability liability and an onboarding wall.)
- **Random id generation (`"plan_"|"step_"|"att_"|"rule_" + Math.random().toString(36).substring(2, 11)`) is duplicated ~8 times** across server.ts (plans, steps, watch rules, attention items) with no `genId(prefix)` helper — the substring bounds even vary (`2,9` vs `2,11`) between sites.
- **`updateSettings` (terminal.ts:643-672) silently ignores unknown top-level keys** and only propagates `maxBufferLines`/`idleTimeoutMs` to live terminals — other advanced changes (e.g. a new live-tunable) would require remembering to add another loop here. No schema-driven application.

## Test-coverage note

- **Tested:** `test_ledger.ts` covers the core ledger CRUD well — init, project create/switch, note persistence, briefing formatting, and watch-rule/plan persist-and-reload round-trip (test_ledger.ts:24-72). `test_journeys.ts` exercises some end-to-end project/voice journeys.
- **Riskiest untested path:** the **plan-advancement state machine in `handlePlansTrigger`** (server.ts:364-510) — the gate-next-step / pause-on-no-session (P0-3) / pause-on-missing-pane branches that decide whether a plan writes, pauses, or completes — has no dedicated unit test (the approvals suite tests the *first* step via `execute_plan`, but multi-step advancement through `handlePlansTrigger` is driven only indirectly). Given it can write to panes, this is the highest-risk untested logic in the chunk. Settings merge/sanitize (`updateSettings` + the API-key mask dance) is also untested.

## Top fixes

1. **Extract a pure `advancePlan(plan, transition, ctx)` module** (returns step-status updates + the next-step gate intent + attention items to enqueue) out of `server.ts:364-510`, and unit-test the advance/pause/complete branches like `decideStatus`. This both shrinks the god-function and covers the riskiest untested path.
2. **Define named `PermissionsMode` / `ToolPreset` / `Transition` type aliases in `types.ts`** and replace the ~15 inline string-literal unions, giving the compiler one place to enforce the vocabulary.
3. **Consolidate the secret-key handling and settings merge** into one place with explicit sentinel constants (`API_KEY_MASK`, `ENV_CONFIGURED`), and add a `saveNow()`/`saveDebounced()` pair to replace `ledger["save"](bool)`.
4. **Move recipes to a typed `recipes.ts` data module** (`const recipes: TemplateRecipe[] = ...`) and add a `genId(prefix)` helper used by all plan/step/rule/attention id sites.
5. **Split `SettingsDialog.tsx` into per-section subcomponents** (Voice, Presets, Advanced, Announcements, Secrets) to drop it well below 300 LOC each and make settings onboarding tractable.
