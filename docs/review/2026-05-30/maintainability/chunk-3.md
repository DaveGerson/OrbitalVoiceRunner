# Chunk 3 — Command Proposal, Permissions & Approvals — Maintainability

**Score: 9/10** — The standout chunk. `approvalIntent.ts` and `pendingApprovals.ts` are textbook clean code: pure, deeply documented, single-responsibility, exhaustively tested; the server glue is a thin renderer over a single pure decision. Points lost only for `sess: any` boundaries, mock-mode simulation leaking into production handlers, and the gate-bypassing handoff path (cross-ref Chunk 2).

## Findings

- **`pendingApprovals.ts` is exemplary.** The split between the serializable `PendingApproval` record and the non-serializable session side-map (pendingApprovals.ts:225-232), the pure `decideProposal` gate (pendingApprovals.ts:105-139), and the single claim-gated `resolveDecision` choke-point (pendingApprovals.ts:176-204) embody SRP and testability-by-design. The header comment (pendingApprovals.ts:1-17) explains the WS-F co-evolution intent so a new dev knows *why* the session handle is separated. This is the model the rest of the codebase should imitate.
- **`approvalIntent.ts` is a genuinely hard problem solved cleanly.** Negation windows, ASR apostrophe-drop, strong/weak verb pairing, and approve/reject collisions are each a named, commented rule (approvalIntent.ts:79-93, 162-169, 193-204) with conservative "never default-approve" semantics. The magic vocab lives in named `Set`s at the top (approvalIntent.ts:30-59), not scattered. Pure and framework-free as advertised.
- **`applyResolution` (server.ts:1181-1223) is a thin, correct renderer** over `resolveDecision`'s `ResolveAction`. The single write path (server.ts:1205), exactly-once narration, and the documented "never a 2nd `sendToolResponse`" invariant (server.ts:1178-1180) are well-handled. `WS_EVT` literals are named in one place with a comment warning that the client keys on the exact strings (server.ts:1161-1171) — good coupling hygiene, though it is still a stringly-typed contract duplicated across the wire (see Chunk 1 fix #2).
- **`dispatchProposal` (server.ts:1303-1358) is a clean switch over `decideProposal`'s tagged union** and is reused by both `propose_command` and `execute_plan` (the R4 path), so plan steps cannot bypass the gate. Good DRY across the two callers.
- **`sess: any` / `session: any` boundary leaks** (pendingApprovals.ts:228,234,260 store the session as `any`; server.ts:1150,1181 pass it around untyped). The store deliberately treats the session as an opaque key (defensible for WS-F), but `pushApprovalNarration(session: any, …)` (server.ts:1150) and `sessionFor(): any` mean a typo'd `.sendClientContent` would not be caught. A minimal `LiveSession` interface would close this without breaking the side-map abstraction.
- **Mock-mode simulation is hardcoded inside the production `handleApprove`** (App.tsx:693-711): an `isMockModeRef` branch fabricates terminal output with literal strings like `"Successfully installed pandas 2.1.0\nDONE"` and a `cmd.includes("tailwindcss")` special-case (App.tsx:704). Demo/mock logic interleaved with the real approval handler is a maintainability smell — it should live behind a mock transport/adapter, not as `if (mock)` branches sprinkled through real handlers.
- **`handleApprove`/`handleReject` swallow all errors** (`catch (e) {}`, App.tsx:720,735) and optimistically remove the pending command from local state *before* confirming server success — a rejected/failed POST leaves the UI out of sync with no user feedback. The `setTimeout(fetchTerminals, 500)` (App.tsx:719) magic-delay reconciliation is a fragile pattern.
- **`effectiveModeFor` (server.ts:1142-1148) hardcodes the `"Human-in-the-Loop"` safe default** as an inline string; the permission-mode strings (`"Full Auto"`/`"Read-Only"`/`"Human-in-the-Loop"`/`"Inherit"`) are repeated as string-literal unions across `terminal.ts`, `pendingApprovals.ts`, `types.ts`, and the UI rather than a single shared const/enum — easy to typo, no exhaustiveness checking.
- **`handoff_context_between_panes` writes to a pane bypassing this chunk's gate** (server.ts:1823-1856, only checks Read-Only, acknowledged TODO(WS-G)) — flagged in Chunk 2, noted here as the one place a write escapes the otherwise-airtight single-dispatch design.

## Test-coverage note

- **Outstanding.** `test_approvals_wse.ts` covers the entire pure surface: `parseApprovalIntent` with a negation/apostrophe/collision table (test_approvals_wse.ts:31-95), `selectApprovalTarget` including the P0-B "fragment-miss must not over-approve" case (test_approvals_wse.ts:144-165), `decideProposal` across all modes/kinds (167-220), the claim-gated `resolveDecision` double-write and expire-vs-approve race (224-281), and end-to-end gate integration including plan-step gating (419-567). `test_approvals.ts` adds concurrency/cleanup/malformed-packet safeguards.
- **Riskiest untested path:** the **client-side `handleApprove`/`handleReject` optimistic-removal + error-swallow** (App.tsx:693-736) has no test, so a failed POST silently desyncing the UI would go unnoticed; and the **`pushApprovalNarration` `sendClientContent` push** (server.ts:1150) — the actual model-facing narration delivery — is mocked away in the integration tests, so a real SDK-shape regression there is uncaught.

## Top fixes

1. **Introduce a single shared `EffectiveMode`/`PermissionsMode` const (or enum)** and import it everywhere the four mode strings appear, replacing the repeated inline string-literal unions and the hardcoded HiTL default.
2. **Extract mock-mode out of the real handlers** — route demo behavior through a mock API adapter so `handleApprove`/`handleCreateTerminal` contain no `isMockMode` branches or fabricated output strings.
3. **Fix client optimistic state + error handling**: only remove the pending command after the approve POST resolves successfully, and surface failures instead of `catch (e) {}`.
4. **Type the live `session`** with a minimal `LiveSession` interface so `pushApprovalNarration` and the store's session handle are checked, without disturbing the WS-F side-map separation.
5. **Route `handoff_context_between_panes` through `dispatchProposal`** so this chunk's gate truly has no bypass (shared with Chunk 2 fix #5).
