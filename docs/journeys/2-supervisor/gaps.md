# Journey 2 — Supervisor / Air-Traffic Control: Gap Register

**Analyst perspective**: Hands-free, eyes-off operator whose sole interaction channel is voice (Janus / Gemini Live audio) and ear (earcons). Screen is irrelevant; every gap is scored by whether it degrades operator safety, awareness, or control.

## 2. Critical and High Gaps — Detailed Analysis

### J2-G1: Janus is fully mute during the approval wait (Critical)

When `propose_command` enters the Human-in-the-Loop branch at `server.ts:1318`, the server deliberately withholds `sendToolResponse`. This is structurally correct for gating execution, but it means the Gemini Live session is hard-blocked at the tool-call level: the model cannot emit audio, cannot call further tools, and cannot speak the proposal aloud. The operator's only signal is the sawtooth earcon. A hands-free operator who receives the earcon with no spoken context must either look at the `ApprovalDialog` (eyes-on) or remember what they said earlier. The deep-dive (`§6.1`) correctly identifies this as the top future-state gap and proposes a two-phase mechanism, but no implementation exists. In multi-agent sessions where proposals arrive asynchronously and the operator is not watching, this is a complete failure of the audio-only safety model.

### J2-G2: No voice-queryable tool for pending approvals (Critical)

The `pendingApprovals` map at `server.ts:978` and the `manager.attentionQueue` are entirely separate data structures. `get_attention_digest` at `server.ts:1360-1373` reads only `manager.attentionQueue`, which is populated solely by terminal state transitions (error, build-failed, exited) at `server.ts:430-443`. A `propose_command` call in HiTL mode never writes to `attentionQueue`. The REST endpoint `GET /api/commands/pending` (`server.ts:980-987`) exposes the map to the UI but is not surfaced as a Janus voice tool. Compounding this, the tool's description at `server.ts:1682-1683` says "items requiring operator confirmation, approvals, or showing error states" — a lie that may cause Janus to call `get_attention_digest` expecting approval data, receive nothing, and incorrectly report to the operator that there are no pending items. No `list_pending_approvals` voice tool exists anywhere in the `functionDeclarations` block (`server.ts:1577-1834`).

### J2-G3: `get_attention_digest` description claims to cover approvals but does not (High)

At `server.ts:1682-1683`, the tool is described as returning "a structured summary of active items in the attention queue requiring operator confirmation, approvals, or showing error states." The word "approvals" and "confirmation" will cause Janus to call this tool when the operator asks "what's pending for approval?" The implementation at `server.ts:1360-1373` returns a count and list of `manager.attentionQueue` items only — pending approvals from `pendingApprovals` are never included. This is not just a documentation inaccuracy; because Janus reasons from the tool description at inference time, it is an active model-steering defect that produces confidently wrong answers to the operator.

### J2-G4: REST approval path omits frontend broadcast events (High)

The voice-intercept approve path at `server.ts:1157-1162` sends a `command_auto_executed` WS event which causes the frontend to fire the `"execute"` earcon and show a toast (`src/App.tsx:904-909`). The voice-intercept reject path at `server.ts:1176-1181` sends a `command_blocked` event which fires the `"alert"` earcon and shows a blocked toast (`src/App.tsx:910-914`). The REST path at `server.ts:989-1028` sends neither broadcast. When the operator approves via the `ApprovalDialog` (keyboard Escape / mouse click), the frontend `handleApprove` / `handleReject` optimistically filters the command from local state and calls `setTimeout(fetchTerminals, 500)` (`src/App.tsx:684-685`), but no earcon fires and no visual confirmation notification appears. An eyes-off operator who happens to use the keyboard receives no audio acknowledgment that the command was dispatched.

### J2-G5: Mock mode `handleApprove` / `handleReject` never hit the server (High)

In mock mode (`isMockModeRef.current === true`), `handleApprove` at `src/App.tsx:660-676` short-circuits before the `apiFetch` call. It manually sets the terminal's `status` to `"Running"`, appends a hardcoded output string — either `"added 1 package, and audited 2 packages in 3s"` if the command mentions "tailwindcss", or `"Successfully installed pandas 2.1.0\nDONE"` otherwise — and returns. `handleReject` at `src/App.tsx:690-693` simply filters the pending command from state with no server call. The mock pre-populates `pendingCommands` with two entries (`"npm install tailwindcss"` and `"pip install pandas"`, `src/App.tsx:1092-1105`) whose IDs are `"mock_msg_1"` and `"mock_msg_2"`. These IDs cannot be found in the server's `pendingApprovals` map since no real `propose_command` tool call was made. This simulated flow teaches operators that approval is instantaneous and always succeeds — the exact opposite of the real flow where the Gemini session is blocked and the terminal must be alive.

### J2-G6: In-memory `pendingApprovals` lost on restart or session drop (High)

The map at `server.ts:978` is a plain JavaScript object with no persistence layer. The WS-close cleanup at `server.ts:1878-1884` silently purges all pending entries for the closing session and logs a console message but sends no operator alert and does not attempt re-queue or disk-write. The `lastSessionResumptionToken` mechanism at `server.ts:1078-1081` and `server.ts:1570` could theoretically allow the Gemini session to resume, but even if the session reconnects, the `pendingApprovals` entries for the old session are already gone and the `session` reference in each entry points to the old, dead session object. The tool call IDs from the previous session are unresolvable. This means any approval that was pending at the time of a network drop is irreversibly lost, leaving the underlying agent task in an ambiguous incomplete state with no notification to the operator.

### J2-G7: Voice approve resolves FIFO first entry only — ambiguous in multi-pane scenarios (High)

At `server.ts:1133-1136`, the voice intercept filters pending entries by session, takes `pendingEntries[0]` (object-key iteration order, which in V8 is insertion order for string keys), and resolves it. If three panes each have a pending proposal and the operator says "approve", the first-inserted command is dispatched with no voice confirmation of which pane or command was resolved. The operator hears only the subsequent `"execute"` earcon from the frontend — which plays on `command_auto_executed` — but the voice response from Janus (`"Command dispatched to {terminalId} successfully via voice."`, `server.ts:1149`) is the only spoken acknowledgment, and that requires the session to have been unblocked first. In a worst-case multi-proposal scenario the operator may approve the wrong command while believing they approved a different one.

### J2-G8: Identical earcon for `approval_pending` and `command_blocked` (High)

`src/App.tsx:877` plays `playEarcon("alert")` on `approval_pending`. `src/App.tsx:911` plays the same `playEarcon("alert")` on `command_blocked`. Both are the 440 Hz / 554 Hz sawtooth double-tone defined at `src/App.tsx:81-100`. The operational meaning is completely different: `approval_pending` demands an immediate operator decision; `command_blocked` is an informational notification that execution was already prevented. An eyes-off operator has no audio cue to distinguish whether they need to act or have already missed the action window.

### J2-G9: No approval TTL — unresolved approvals freeze Gemini session indefinitely (High)

The `pendingApprovals` map stores no timestamp and has no expiry logic. A `propose_command` tool call in HiTL mode holds the Gemini session open with no `sendToolResponse` indefinitely. The only cleanup path is WS close (`server.ts:1878-1884`), which destroys rather than times out the entry. If the operator is interrupted, loses audio, or simply forgets about the pending approval, the session remains frozen and Janus is mute for the entire duration. There is no countdown earcon, no auto-reject fallback, and no configurable TTL.

## 3. What's Solid

The core gating mechanism is correctly implemented and production-worthy. `propose_command` at `server.ts:1267-1335` faithfully enforces all three permission branches (Full Auto, Read-Only, Human-in-the-Loop) with proper `effectivePermissions` resolution from global → pane → default. The voice intercept at `server.ts:1127-1186` is genuinely hands-free: any user utterance containing an approval keyword resolves the earliest pending entry without requiring a screen interaction. The earcon system at `src/App.tsx:73-151` provides immediate audio feedback via Web Audio API synthesis with no external dependencies. The `ApprovalDialog` correctly auto-focuses the Reject button and binds Escape to rejection (`src/components/ApprovalDialog.tsx:22-32`), giving keyboard-only operators a safe default. The `rationale` block (pane snapshot + trigger utterance) is surfaced in both the dialog and the pending-commands REST response, giving the operator context even when they do look at the screen. Session cleanup on WS close (`server.ts:1878-1884`) prevents memory leaks and orphaned Gemini tool calls. The 3-second REST poll (`src/App.tsx:593-599`) provides a reconnect safety net. The `lastSessionResumptionToken` infrastructure (`server.ts:1078-1081`, `1570`) exists and is wired, providing a foundation for eventual persistence-based reconnection.
