## 2. Critical and High Gaps — Detail

### J3-G1 — Janus never vocalizes the proposed command (Critical)

This is the most fundamental eyes-off safety failure in the journey. The entire HitL gate assumes the operator can hear what they are approving, but the system provides no mechanism for that. When `propose_command` is intercepted at `server.ts:1318–1334`, the server sends an `approval_pending` WebSocket message to the frontend and plays a two-tone earcon (`src/App.tsx:877`). That is the entirety of the ears-off signal. The Janus system prompt (`server.ts:1568`) contains no instruction to verbalize the command string before or after calling `propose_command`. The `propose_command` tool description at `server.ts:1588` says only "Triggers human approval; returns the outcome." The Gemini Live session's audio stream has already concluded by the time the tool call is emitted — Janus says nothing aloud about what it is proposing. The only way an eyes-off operator learns the command is by asking Janus to repeat it (via `get_pane_command_history` or free-form question), but that requires knowing to ask. Without the verbal announcement, every voice approval is a blind approval.

### J3-G2 — Naive substring parser with no negation detection (Critical)

The voice interception parser at `server.ts:1127–1129` is a flat `Array.prototype.some + String.prototype.includes` scan. It will misfire on any utterance that contains a trigger substring in a negated or incidental context. Confirmed failure modes include: "I don't want to cancel the build" (contains `"cancel"`) triggers a rejection of whatever command is oldest in `pendingApprovals`; "we need to execute this carefully before pushing" (contains `"execute"`) triggers an approval; "actually let me not go ahead and approve that yet" (contains both `"go ahead"` and potentially `"approve"`) triggers an approval. The `isApprove` / `isReject` collision case (`server.ts:1139`) compounds this: when both flags are `true`, `if (isApprove)` fires first and the command executes with no indication to the operator that a collision occurred. There is no confidence threshold, no context window, and no disambiguation request back to the operator. In a hands-free scenario where the operator is narrating their thought process aloud, any of these phrases spoken incidentally will silently dispatch or cancel a command.

### J3-G3 — Multi-pending always resolves the oldest entry regardless of pane focus (Critical)

When multiple `propose_command` calls are pending across different panes, the voice parser filters `pendingApprovals` to entries matching the current session, then unconditionally takes `pendingEntries[0]` at `server.ts:1136`. The comment at line 1135 reads "Sort to resolve the earliest/most relative first" but no `.sort()` call is present; `Object.entries` returns insertion order in V8, which is effectively FIFO. This means the oldest pending command — regardless of which pane the operator is currently discussing or has focus on — is always the one resolved by a generic "approve" or "reject" utterance. In a scenario where Janus has queued `rm -rf build/` on pane A (older) and `npm install` on pane B (newer), an operator saying "approve the npm install" who expects to approve pane B will actually execute `rm -rf build/` on pane A, with no warning or confirmation that the resolved command was the one intended. This is a direct eyes-off command-execution safety risk.

### J3-G4 — `isApprove` silently wins on ambiguous utterances (High)

When `isApprove` and `isReject` are both `true` simultaneously — which can occur with utterances like "execute that but cancel the other one" or "run it, actually reject, no go ahead" — the `if (isApprove)` branch at `server.ts:1139` executes unconditionally. The `isReject` branch is an `else`, so it is never reached when `isApprove` is true. The operator receives no feedback that their utterance was ambiguous; Gemini receives a `Command dispatched...via voice` tool response and proceeds to speak a confirmation. The correct behavior is to detect the collision, emit a clarification request via Gemini (`sendToolResponse` with a question asking for disambiguation), and withhold execution until a clean approval signal is received.

### J3-G5 — `"don't run"` apostrophe fragility in ASR (High)

The rejection keyword list at `server.ts:1129` includes the literal string `"don't run"` — a Unicode right-apostrophe or straight-apostrophe form depending on how it was typed. Gemini Live ASR transcriptions routinely produce `"dont run"` (no apostrophe) for spoken "don't run." The `.includes("don't run")` check will fail against `"dont run"`, silently missing the rejection intent. This is not a corner case: voice-to-text apostrophe handling is inconsistent across ASR engines. An operator who says "don't run that" expecting a cancellation will find the command remains pending with no feedback that their utterance was unrecognized.

### J3-G6 — `pendingApprovals` shared across connections; REST has no session check (High)

`pendingApprovals` is declared at `server.ts:978` inside `startServer()` but outside the `wss.on("connection")` callback (line 1032), making it a server-wide shared map. The voice path performs session scoping via `details.session === session` at `server.ts:1133`, which limits voice approvals to the current WebSocket connection's Gemini session. However, the REST endpoint `/api/commands/approve` at `server.ts:989–1028` does a direct `pendingApprovals[messageId]` lookup with no session or connection check. Any authenticated browser tab that knows (or can observe from the `/api/commands/pending` GET endpoint at `server.ts:980–987`) a `messageId` from another tab's session can approve or reject that session's pending command. In a multi-tab or multi-user scenario (e.g. demo environment, shared workstation), this creates cross-session command injection.

### J3-G7 — No approval timeout: Gemini session freezes indefinitely (High)

When `propose_command` is intercepted in HitL mode, the server deliberately withholds the tool response (`server.ts:1334`). Gemini Live is left waiting for a `sendToolResponse` call. If the operator fails to speak an approval or rejection utterance — whether because they did not hear the earcon, spoke a phrase not in the keyword list, or simply walked away — the Gemini session remains suspended with no recovery path. There is no `setTimeout` or TTL anywhere in the `pendingApprovals` lifecycle (confirmed by search: the only timeout in the server is a stdout-flush debounce at `server.ts:469`). The session will eventually time out at the Gemini API level, but the client receives no informative message and the pending command entry is only cleaned up on WebSocket close (`server.ts:1879–1884`). This means a frozen session can persist for the lifetime of the WebSocket connection.

### J3-G8 — `get_attention_digest` omits pending approvals (High)

The `get_attention_digest` tool at `server.ts:1360–1373` iterates only `manager.attentionQueue` (state-transition alerts). It has no reference to `pendingApprovals`. An operator asking Janus "what needs my attention?" will hear about idle/error state transitions but will not hear "you also have 2 commands waiting for your voice approval." This breaks the primary eyes-off discovery path for pending commands. The only in-band discovery mechanism is the earcon played at approval time (`src/App.tsx:877`) — which is not repeated. If the operator missed the earcon, they have no way to recover without visually checking the UI or explicitly asking Janus about pending commands (which Janus has no dedicated tool to answer from its toolset).

## 3. What's Solid

The core `approve`/`reject` execution path is correctly wired end-to-end. When the voice parser does fire correctly, `term.writeInput`, `HistoryManager.addCommand`, and `pending.session.sendToolResponse` all execute atomically before `delete pendingApprovals[messageId]` at `server.ts:1183`, ensuring the Gemini session is unblocked and the frontend is notified. The `vocal: true` flag on the voice path (`server.ts:1161`) correctly distinguishes voice-originated approvals from UI clicks in the frontend handler. Session cleanup on WebSocket close (`server.ts:1878–1884`) correctly prevents tool-call leaks by iterating all pending entries and deleting session-matched ones before calling `session.close()` — verified by `tests/test_approvals.ts:44–72`. The deduplication guard in `setPendingCommands` at `src/App.tsx:880` prevents duplicate dialog entries for the same `messageId`. The `ApprovalDialog` displays the trigger utterance and pane summary snapshot (`rationale`) from the moment of interception, giving sighted users meaningful context. The `Escape` key binding on `ApprovalDialog` (`ApprovalDialog.tsx:23–31`) with `autoFocus` on the Reject button (`ApprovalDialog.tsx:75`) makes keyboard-accessible rejection the default path, which is a good safety default for non-voice scenarios.
