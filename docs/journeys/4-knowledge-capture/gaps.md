## 2. Critical & High Gaps (Detailed)

### J4-G3 — CRITICAL: `summarizeCommandOutcome` calls a non-existent model

The sole AI summarization step in the knowledge pipeline — `summarizeCommandOutcome` at `server.ts:187-218` — hardcodes `model: "gemini-3.5-flash"` (line 210). No such model exists in the Google Generative AI API as of 2025; the currently valid flash-tier model names are `gemini-2.0-flash` and `gemini-2.5-flash`. Every call to this function throws an API-level error, which is caught silently by the `try/catch` at lines 214-217 and replaced with the fallback string `"Execution finished successfully."`. This means the `finalResponse` field for every history entry in `.janus_history.json` is not a summary of the actual command outcome — it is a meaningless placeholder. When Janus calls `get_pane_command_history`, it receives a list of `{command, timestamp, finalResponse: "Execution finished successfully."}` objects that convey no real information. The `handoff_context_between_panes` handler (lines 1525-1526) also uses these `finalResponse` values to build the handoff note, meaning every handoff is contaminated with the same placeholder text. The impact propagates across all three sub-journeys: capture, re-briefing, and handoff. The fix is a single-line model name correction, but the problem affects all downstream continuity features.

### J4-G1 — HIGH: Notes are untyped, unordered plain strings

Both `Workspace.notes` (src/types.ts:43) and `PaneMeta.notes` (src/types.ts:30) are `string[]`. There is no timestamp, no type tag (`decision`/`TODO`/`warning`/`handoff`), and no author field (`janus` vs `user`). This means: (a) notes are append-only with no chronological ordering visible to the operator unless they happen to be dictated in order; (b) voice queries like "what decisions did we make?" or "show me TODOs" cannot be answered without Janus scanning the entire array with no structural cues; (c) handoff notes (written by `handoff_context_between_panes` at server.ts:1529-1531) are indistinguishable from regular operator notes; (d) there is no way to expire or archive old notes. The `Ledger.addNote` and `addPaneNote` methods (src/ledger.ts:181-186, 158-163) simply push a raw string with no enrichment. Tests in `tests/test_ledger.ts:36-50` verify the string values directly, confirming no metadata structure is tested or expected. This is the foundational schema gap: all other note-quality improvements (search, filtering, deletion by ID) are blocked until the data model is upgraded.

### J4-G4 — HIGH: Command history is architecturally siloed from the briefing

The `Ledger` and the `HistoryManager` are independent systems stored in separate files (`.janus_ledger.json` vs `.janus_history.json`). The `getProjectBriefing` method (src/ledger.ts:197-209) returns notes, summary, panes, directory, and key terms — but no history. The `switch_context` handler (server.ts:1255-1266) returns only the briefing payload. An operator who says "brief me on this project" receives zero information about what commands were recently run. To assemble a complete picture, Janus must call `get_pane_command_history` once per pane (each requiring an explicit tool call and a round-trip). In a voice-only session with multiple active panes, this creates an awkward multi-step interview pattern where the operator must prompt each individual pane history. Furthermore, because history is keyed by `terminalId` (a runtime identity that changes across restarts, server.ts:53-54), there is no reliable cross-session cross-pane aggregate timeline. The briefing and history silos should be bridged by a `HistoryManager.loadAllHistory(paneIds[])` method whose output is injected into `getProjectBriefing` as a `recent_commands` field.

### J4-G5 — HIGH: Handoff produces no persistent named artifact

`handoff_context_between_panes` (server.ts:1516-1541) and its REST equivalent (server.ts:909-930) deliver context in two ways: (1) a bash comment block written directly to the target pane's stdin via `targetTerm.writeInput(commentCommand)` — this scrolls off the screen within seconds and is unrecoverable; (2) a single untagged pane note string added via `addPaneNote`. The pane note has no type field, no `handoff` tag, and is stored alongside all other notes with no distinguishing attribute. A future operator or a second Janus session cannot ask "show me the last handoff" because there is no query mechanism and the handoff note looks identical to any other note. The success response string (`"Successful handoff orchestrated from... Handoff packet injected into active process thread streams."`) implies a richer artifact was created, but nothing of the sort exists in the codebase. The `Workspace` interface (src/types.ts:37-45) has no `handoffs[]` field. This means every cross-pane handoff in OrbitalVoiceRunner is effectively ephemeral from the operator's continuity perspective.

### J4-G6 — HIGH: Session resumption token is not persisted across server restarts

`lastSessionResumptionToken` is declared as a module-level `let` variable at server.ts:1030. It is populated from Gemini's `sessionResumptionUpdate` messages (server.ts:1078-1080) and passed back on WebSocket reconnect (server.ts:1570). However, because it lives only in process memory, any server restart (SIGTERM, crash, deployment) discards it. After a restart, `lastSessionResumptionToken` is null, and the next Gemini Live session starts with no resumption token — meaning the model's live conversation context window is lost. Notes and history survive (they are on disk), but Gemini has no memory of prior turns, function calls, or context compression state. For a voice-first continuity product, this is a meaningful regression: an operator returning after a server bounce expects Janus to pick up where it left off, but instead encounters a fresh session that requires re-briefing from scratch.

### J4-G2 — HIGH: `switch_context` briefing is a raw JSON dump with no synthesis

The `getProjectBriefing` method (src/ledger.ts:197-209) returns a plain JSON object. No server-side prose is assembled. The Gemini model must verbally narrate this JSON in real-time from within its context window. This creates two problems: (a) if the context window is approaching the compression threshold (`triggerTokens: 25000`, server.ts:1572), the `slidingWindow` compression (server.ts:1573) may have already dropped earlier conversation turns, meaning the model narrates without the benefit of prior conversational context; (b) the verbal briefing is non-deterministic and non-testable — there is no way to assert what Janus will actually say. Meanwhile the `summarizeCommandOutcome` path already demonstrates that server-side AI synthesis is architecturally feasible. The briefing path should follow the same pattern, with a cached 3-5 sentence narrative generated on the server and returned alongside the raw JSON.

### J4-G7 — MEDIUM: JOURNEYS_DESIGN.md §4 documents capabilities that do not exist

`JOURNEYS_DESIGN.md` line 82 states: "the system instruction is reconstructed dynamically with available workspaces, file trees, notes, and the live status indicators of all terminals." The actual system instruction at server.ts:1568 contains only: active project ID, workspace ID/name pairs, and terminal status/CWD values. Neither notes content nor file trees appear anywhere in the template string. This discrepancy means an operator or developer reading the design document will build incorrect mental models and workflows (e.g., assuming notes automatically surface to Janus on every session without a `switch_context` call). The comment on server.ts:1568 itself acknowledges the minimal design: "Always use switch_context to get the full project briefing when starting." The design document contradicts this comment and needs to be corrected or the code needs to be updated to match it.

## 3. What's Solid

The following components work as designed and provide a genuine, reliable foundation for the knowledge capture journey:

**Atomic ledger persistence** (`src/ledger.ts:89-127`): Both the async (`flushSave`) and sync (`flushSaveSync`) paths write to a temp file first and rename atomically. Notes and workspace metadata survive process restarts and concurrent writes without corruption.

**Note persistence through restart** (confirmed by `tests/test_ledger.ts:36-50`): `addNote` and `addPaneNote` write synchronously (`save(true)`) and are covered by a persistence round-trip test that creates a second `Ledger` instance from the same file and asserts note values are intact.

**REST + voice dual capture paths**: Both `POST /api/projects/:id/notes` (server.ts:634-639) and the `add_project_note` voice tool (server.ts:1336-1341) delegate to the same `Ledger.addNote` codepath, ensuring parity between UI-driven and voice-driven note capture.

**History summarization architecture is sound in principle**: `HistoryManager` (server.ts:41-129) correctly loads per-pane history, limits it by configurable `historyMaxCommands`/`historyMaxOutputLength` (src/types.ts:93-94), and the `onIdle` hook (server.ts:220-246) fires the summarization at the right moment (after the pane returns to idle). The only defect is the invalid model name (J4-G3); the wiring is otherwise correct.

**Handoff ledger note does persist**: Despite the transient stdin injection, the `addPaneNote` call in `handoff_context_between_panes` (server.ts:1531) does write a durable record to `.janus_ledger.json`. An operator or Janus can retrieve it via `switch_context` + inspecting pane notes. It is merely untagged and unsearchable — not fully absent.

**Dual delivery path for handoff (voice + REST)**: The tool handler (server.ts:1516-1541) and the REST endpoint (server.ts:909-930) share identical logic, meaning the handoff is reachable from both the Synergy Console UI and from voice, without code divergence.

**Context window compression is configured**: `contextWindowCompression` with `triggerTokens: 25000` and `slidingWindow.targetTokens: 16000` (server.ts:1572-1574) is active, reducing the risk of context overflow during long sessions, even if it does not fully replace the need for server-side briefing synthesis.
