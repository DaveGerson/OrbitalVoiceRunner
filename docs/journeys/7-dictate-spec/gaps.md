## 2. Critical and High Gaps — Narrative

### J7-G1 — Prompt buffer not persisted (Critical)

The `promptBufferText` variable is declared as a bare module-level `let` at `server.ts:133`. Every utterance — both user dictations and Janus responses — is appended to it at `server.ts:1120` and `server.ts:1200`, but no code path ever writes this string to disk. The `.janus_ledger.json` serialization in `src/ledger.ts:91-96` serializes only `activeProjectId`, `workspaces`, `watchRules`, and `plans` — `promptBufferText` is not in the schema. On any server restart (crash, redeploy, accidental kill) every ambient spec fragment the operator has spoken is permanently gone. The UI label "Shared Spec Sandbox: Janus reads this buffer in real-time" (`src/App.tsx:1593`) makes no mention of this volatility, creating a false expectation of durability. This is the highest-severity gap in the journey because it is invisible to the operator and affects the most common capture path (ambient dictation).

### J7-G2 — Only bridge from buffer to ledger is keyboard-only and truncates (Critical)

`handleSyncNoteToActiveNode` at `src/App.tsx:222-232` is the sole mechanism to promote a buffer fragment to a durable ledger note. It is bound to a click-only "Sync Note" button (`src/App.tsx:1639-1645`) and it hardcodes a 100-character slice: `promptBuffer.slice(0, 100).replace(/\n/g, " ")`. For a voice-dictated spec of any real length — "the auth service must support PKCE, not implicit flow; the token endpoint must not accept grant_type=password; the refresh window is 30 days" — the stored note would read `"Requirement Spec Captured: the auth service must support PKCE, not implicit flow; the token en..."` and nothing beyond. There is no voice tool in the entire `server.ts` tool list (`server.ts:1579-1655`) that can trigger a buffer commit. The operator who is heads-down, hands-off cannot make any spec note durable without physically reaching for a keyboard. Combined with J7-G1, this means the only durable path (explicit `add_project_note`/`add_pane_note` via voice) works when Janus decides to invoke those tools, but the ambient capture path has no durable landing zone at all.

### J7-G3 — Notes stored as raw unstructured strings with no metadata (High)

Both `PaneMeta.notes` and `Workspace.notes` are typed as `string[]` in `src/ledger.ts:4-16`. The tool schemas at `server.ts:1632-1654` accept only `project_id`, `pane_id`, and `note` (all raw strings). The `addNote` and `addPaneNote` methods at `src/ledger.ts:181-186` and `158-163` push the verbatim string with zero transformation. There is no timestamp, no category, no priority, no source flag (voice vs. keyboard vs. import), and no unique note ID. Consequences are compounding: (1) Janus cannot speak "you have 2 security-critical notes"; (2) the operator cannot say "delete the last security note" without an index; (3) `getProjectBriefing` (`src/ledger.ts:197-209`) returns a flat `notes: string[]` with no structure to help Janus prioritize what to surface in the opening briefing; and (4) no search or filter is possible. This gap is foundational — resolving it requires a schema change to `src/types.ts` and `src/ledger.ts` before higher-level features (voice search, export, categorized briefing) can be built on top.

### J7-G4 — No voice tool to delete or amend a note (High)

The tool registry at `server.ts:1579-1655` contains `add_project_note` and `add_pane_note` but no `delete_project_note`, `delete_pane_note`, `amend_note`, or any equivalent. `src/ledger.ts` has no `deleteNote` or `amendNote` method. The UI renders notes as a read-only list at `src/App.tsx:3382-3387` and `src/App.tsx:2530-2534` with no per-note edit or delete control. A transcription error committed to the ledger is permanent unless the operator manually edits `.janus_ledger.json` on disk. This directly contradicts the hands-free modality promise and the ideal experience stated in the deep-dive (§3 step 6).

### J7-G5 — Notes only surface to Janus on `switch_context`, not continuously (High)

`getProjectBriefing` at `src/ledger.ts:197-209` is the only function that returns persisted notes as structured data, and it is called exclusively inside the `switch_context` handler at `server.ts:1263`. The Gemini session system instruction at `server.ts:1568` is constructed once at session start and does not include any note content — it lists workspace IDs and live terminal IDs only. This means if an operator dictates "note that the API must be rate-limited" and Janus calls `add_project_note` successfully, then the operator asks ten minutes later "Janus, remind me what I just noted about the API" — Janus cannot answer from its current context without calling `switch_context` again, which is a full context reset. This creates a discontinuous spec experience where notes are durably stored but contextually invisible mid-session.

### J7-G6 — `add_pane_note` requires explicit pane ID with no active-pane default (High)

The `add_pane_note` tool schema at `server.ts:1644-1654` marks `pane_id` as required. The system instruction at `server.ts:1568` lists live pane IDs in a comma-separated string but does not flag which one is currently active from the frontend's perspective (the client-side `activeTerminalId` React state at `src/App.tsx:222` is never transmitted to the server for injection into the Janus context). The "Sync Note" button at `src/App.tsx:222-232` uses `activeTerminalId` correctly, but that is a keyboard path. When the operator says "note this on the current pane", Janus must guess which pane is active or ask, adding spoken friction to a voice-only workflow.

### J7-G7 — No lightweight voice tool to retrieve or search notes (High)

The only way to retrieve persisted notes by voice today is to call `switch_context`, which returns the full project briefing including `notes[]`. There is no `get_project_notes`, `list_notes`, or `search_notes` tool in the registry at `server.ts:1579-1655`. The operator cannot say "Janus, what notes do I have on this project?" without triggering a full context switch, nor can they say "find the note about rate limiting" to search by keyword. This makes the ledger write-only from a voice interaction standpoint and means dictated specs are effectively dark until the next session's opening briefing.

## 3. What's Solid

The foundational write path for deliberate spec capture is correctly implemented and reliable. When Janus decides to call `add_project_note` or `add_pane_note`, the handler at `server.ts:1336-1347` calls `ledger.addNote` / `ledger.addPaneNote` which both invoke `save(true)` — the synchronous atomic write via `.tmp` rename at `src/ledger.ts:110-127`. The note is on disk before the tool response is sent back to Gemini. The atomic rename pattern (`writeFileSync` to `.tmp`, then `renameSync`) correctly prevents torn writes. The WebSocket `broadcastLedgerUpdate()` call immediately refreshes the React UI, so keyboard-visible users see the note appear in the "Node Chronicle" pane (`src/App.tsx:3375-3408`) in real time. Test coverage for the persistence path is present and correct: `tests/test_ledger.ts:36-50` verifies round-trip persistence across `Ledger` re-instantiation for `addNote`, and the test correctly asserts both the count and the verbatim string value. The REST note append endpoints at `server.ts:634-639` and `server.ts:648-653` are clean single-responsibility handlers. The `getProjectBriefing` method at `src/ledger.ts:197-209` correctly returns the full `notes[]` array as part of the briefing object, so once `switch_context` is called the notes are available in Janus's context. These pieces form a solid foundation that the missing gaps above should be built on, not around.
