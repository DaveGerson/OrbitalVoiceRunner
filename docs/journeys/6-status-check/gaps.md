## 2. Critical and High Gaps — Extended Analysis

### J6-G1: 1-Second Idle Timeout (Critical)

The most damaging gap in Journey 6. Any process that stops emitting output for more than 1 second will have its `status` set to `"Idle"` by the `setTimeout` at `src/terminal.ts:179–188`, regardless of whether it is still executing. This is the normal behavior for nearly every meaningful long-running operation: TypeScript compilation, `npm install`, test suite runs, database migrations, AI agent "thinking" pauses, large file I/O, and network requests. In all these cases, `is_busy` reports `false` and `last_known_state` says `"Idle"` while the process is actively running. When the operator asks "what's running right now?" during a 2-minute compilation, Janus will truthfully relay `is_busy=false` — the exact opposite of the truth. There is no way for the operator to distinguish a genuinely idle pane from a silently busy one. This gap makes the central field of the status-check journey (`is_busy`) untrustworthy for any workload beyond trivially fast commands, and it is the architectural root cause of the largest Journey 6 UX failure. The fix requires replacing the timer with an authoritative signal: either a unique sentinel string written to the PTY stdin whose echo in stdout marks "command has returned to prompt", or a `/proc/[pid]/stat` check for Linux subprocess state.

### J6-G2: Prompt-Pattern False-Idle on Non-Prompt Output (Critical)

The regex `/([\?$#>]|\[[yY]\/[nN]\]|\([yY]\/[nN]\)|password:|confirm\??)\s*$/i` at `src/terminal.ts:163` is applied to the last line of the current output chunk and to the last 5 lines of buffered output (`fullStripped`). The characters `$`, `#`, `>`, and `?` are extremely common in legitimate output: dollar amounts (`$19.99`), comment lines in shell scripts (`# step 1`), XML/HTML (`</tag>`), Python interactive output, AI agent formatted output, and build tool progress lines. Any of these will instantly flip `status` to `"Idle"` and call `onIdle`, potentially triggering watch rules or plan advancement prematurely at `server.ts:445–446`. This interacts badly with AI agent panes (Claude Code, Codex) whose output routinely contains markdown code blocks with `$` prefixes. The check on `fullStripped` — the concatenation of the last 5 lines — amplifies the problem: a false-positive pattern buried several lines back in the output buffer will still trigger the idle flip even if the current line is innocuous.

### J6-G3: Heuristic Entirely Untested (Critical)

Both the Journey 6 test (`tests/test_journeys.ts:212–237`) and the terminal manager unit test (`tests/test_terminal_manager.ts:14–32`) test only the `syncLedger` propagation path: they manually set `term.status = "Running"` or `term.status = "Idle"` and verify that `listPanes()` returns `is_busy=true/false` accordingly. Neither test ever sends a raw output chunk through `updateStatusOnOutput`. The heuristic detection — the 1-second timer, the prompt-pattern regex, the `wasRunning` guard — has zero test coverage. Any future change to the heuristic (timeout value, regex, buffer depth) would not be caught by CI. Combined with J6-G1 and J6-G2, this means the most failure-prone code in the journey is also the most invisible to automated validation.

### J6-G4: No Elapsed-Time Data (High)

`PaneMeta` at `src/ledger.ts:4–16` has no timestamp field. `syncLedger` at `src/terminal.ts:564–591` overwrites `is_busy` and `alive` on every call but records no `last_status_change_at`. The `list_panes` response therefore carries no temporal context. For a hands-free operator, "pane X is running" and "pane X has been running for 18 minutes" have radically different implications: the first is normal, the second signals a possible hang. Without elapsed time, the operator has no way to identify stuck panes without watching a clock.

### J6-G5: No Proactive Audio Push on Completion or Error (High)

The `onIdle` callback at `src/terminal.ts:173–175` fires whenever a pane transitions Running→Idle. It is wired through `OrchestratorManager` at `terminal.ts:539–541`, but the registered handler at `server.ts` only feeds watch rules (`handleWatchRulesTrigger`) and plan advancement (`handlePlansTrigger`). It never sends a WebSocket event that would prompt Janus to speak. Similarly, `detectAndTriggerTransitions` at `server.ts:430–442` pushes `AttentionItem`s and broadcasts `attention_updated` to connected browser clients (which updates the visual badge count), but this WS event is not interpreted by the Janus Gemini Live session — there is no mechanism to interrupt Janus with a push notification. The operator must actively ask at the right moment to learn that a pane finished or errored. In a true hands-free, eyes-off context, this is a fundamental modality mismatch: the whole point of the setup is that the operator is not watching the screen.

### J6-G6: Detached Process Groups and `alive` Correctness (High)

All non-Windows terminals are spawned with `detached: true` at `src/terminal.ts:255–259`, using `script -q -f -c ...` as the executable. The `script` process creates its own session and process group. If `script` exits (e.g., its child shell exits), Node fires `process.on('exit')` and `process.on('close')` at `terminal.ts:309–315`, setting `status = "Exited"` and thus `alive = false`. However, if a grandchild process (e.g., an AI agent forked by the shell) survives `script`'s exit — which `detached: true` explicitly permits — those processes continue running as orphans while `alive=false` is reported. Conversely, if `script` itself becomes a zombie (PID visible but not processing) without firing Node's close event, `alive` will remain `true` indefinitely. The `detached: true` flag increases the probability of both scenarios. There is no watchdog or `kill(pid, 0)` probe to catch these states.

## 3. What's Solid

**`alive` field reliability.** The `alive` signal is driven directly by Node.js `child_process` events (`process.on('exit')`, `process.on('close')`, `process.on('error')`) at `src/terminal.ts:304–315`. These are synchronous event-loop signals that Node fires reliably when the immediate child process terminates. For the common case where no grandchild survives the `script` wrapper, `alive=false` is a trustworthy indicator.

**`syncLedger` freshness on demand.** `listPanes()` calls `syncLedger()` before returning (`src/terminal.ts:551–552`), ensuring that the data Janus receives reflects `term.status` at the exact moment of the tool call. There is no caching layer that could return stale ledger data.

**`get_attention_digest` correctness for known error events.** The attention queue is populated by `detectAndTriggerTransitions` at `server.ts:430–442`, which is called on every output chunk. Error keywords (`build failed`, `Error:`, `Traceback`, etc.) and `process.on('exit')` events are reliably captured. For events that did produce output matching those patterns, `get_attention_digest` returns an accurate, complete list. The `AttentionItem` type at `src/types.ts:101–110` includes a `timestamp` field, preserving the full event record.

**`detectAndTriggerTransitions` → plan/watch-rule wiring.** The transition detection at `server.ts:379–447` correctly feeds both `handleWatchRulesTrigger` and `handlePlansTrigger`, meaning automated downstream actions (watch rules, plan steps) do fire on completion and error events. The infrastructure for reacting to terminal state changes exists; it simply stops short of pushing audio to Janus.

**Ledger persistence.** `syncLedger` saves to `.janus_ledger.json` (async, debounced) on every call. Terminal state survives server restarts to the degree captured in the ledger, and the `save(false)` at `src/terminal.ts:590` ensures the write is not blocking.
